# 赛题 4：QLoRA 训练时长估算与自动关机（2026-10-06）

## 微调方法的来源

当前配置是 **4-bit QLoRA SFT**。LLaMA-Factory 用 bitsandbytes 将预训练底座按默认 NF4 进行 4-bit 加载，并启用 double quantization；底座参数冻结，前向/反向以 BF16 计算，只训练 LoRA 低秩矩阵（本次约 4328 万个可训练参数）。保存的是 adapter，原 Qwen3.5-9B 权重另存于服务器忽略目录。这不是全参数微调，也不是将量化后的全部权重重新训练。

理论与实现来源分别是 [LoRA（Hu 等，2021）](https://arxiv.org/abs/2106.09685)、[QLoRA（Dettmers 等，2023）](https://arxiv.org/abs/2305.14314)、[LlamaFactory（Zheng 等，ACL 2024）](https://aclanthology.org/2024.acl-demos.38/) 及其[官方 v0.9.5 实现](https://github.com/hiyouga/LlamaFactory/releases/tag/v0.9.5)。[Qwen3 官方仓库](https://github.com/QwenLM/Qwen3#finetuning)将 LLaMA-Factory 列为可用框架之一；[Qwen3.5-9B 模型卡](https://huggingface.co/Qwen/Qwen3.5-9B)没有指定唯一的微调框架。16K 时显存不足发生在全词表损失计算，[Liger Kernel](https://github.com/linkedin/Liger-Kernel)的 Qwen3.5 融合线性层交叉熵让相同 16356-token 样本完成反向传播。LoRA rank、学习率、A/B/C 混合与金标链抽样是本题的工程初始设定，需要固定包验证集检验；论文没有证明这些具体数值对本题最优。

## 一轮训练的时间预测

正式配置 `experiments/configs/task4_qwen35_9b_llamafactory_fit_16k.yaml` 对 11538 条已筛选 fit 行运行一轮，约 8282 万 token；batch 1、梯度累积 8，预计约 1443 次优化器更新。真实模板下长度中位数 6538 token，90 分位 11024 token。GPU 单步实测如下，均在 RTX 4090、4-bit QLoRA、Liger、BF16、batch 1 下完成：

| 样本长度 | 训练段耗时 |
| ---: | ---: |
| 约 4K | 8.3 秒（自动关机演练的短样本） |
| 8194 | 27.7 秒 |
| 12270 | 52.2 秒 |
| 16356 | 82.9 秒 |

按 11538 行的长度区间和单步曲线估算，纯样本训练约 76 小时；长度区间内位置不确定时，模型计算约 60–93 小时。考虑优化器更新、检查点、数据加载及运行波动，给预算用的区间是 **70–100 小时，即约 3–4 天/轮**。这是推算，不是完整一轮实测。当前 Qwen Gated DeltaNet 使用 Transformers 的 torch fallback；若以后安装并验证更快的算子，时长可能变化，不能沿用这份预测。平台按量实例是否停机止费、关机后 GPU 是否保留见 [AutoDL 计费说明](https://api.autodl.com/docs/price/)；包年包月预付费实例关机不会立即退回租期费用。

## 自动关机守护脚本

`experiments/train_shutdown_guard.py` 负责启动训练、记录退出码、检查最终 adapter、`trainer_state.json` 与 `train_results.json`，并在达到设定步数后才开始监控 GPU。默认阈值是 GPU 利用率不超过 **5%**、已用显存不超过 **2048 MiB**、没有其他 GPU 计算进程，连续 **10 分钟**。训练期间短暂的低 GPU 利用率不会被当成完成；查询 GPU 失败会重置连续空闲计时。实际关机还要求显式 `--arm-shutdown`，运行于 root，调用本机平台提供的 `/usr/bin/shutdown`。日志和状态都在 Git 忽略的 `outputs/`。

已在服务器以 `--no-shutdown --idle-minutes 1` 做完整演练：守护脚本在 SSH 分离后完成一步训练、核对 adapter 和训练状态、观测 GPU 连续空闲，最终状态为 `verified_no_shutdown`，服务器保持运行。单元测试另外验证了训练失败、步数不足、产物缺失和 GPU 利用率回升时不能触发关机。真实关机动作没有演练；它只会在以后正式运行时加入 `--arm-shutdown` 才执行。

正式训练时，在服务器上执行下面命令后可离开 SSH；`nohup` 与 `setsid` 使守护脚本独立于终端。请确保当前配置的正式输出目录尚不存在，旧运行的日志和状态文件也未占用同名路径。

```bash
cd /root/autodl-tmp/event-causal-chain-repo
nohup setsid /root/autodl-tmp/task4-qwen35-venv/bin/python \
  experiments/train_shutdown_guard.py \
  --config experiments/configs/task4_qwen35_9b_llamafactory_fit_16k.yaml \
  --arm-shutdown --min-steps 1000 \
  --utilization-limit 5 --memory-limit-mib 2048 --idle-minutes 10 \
  > outputs/llamafactory_logs/qwen35_fit_guard.launch.log 2>&1 < /dev/null &
```

可用 `cat outputs/llamafactory_logs/task4_qwen35_9b_llamafactory_fit_16k.watch.json` 查看阶段，用 `tail -f outputs/llamafactory_logs/task4_qwen35_9b_llamafactory_fit_16k.train.log` 查看训练日志。运行前也可用 `--check-existing` 对已完成的压力测试输出做只读验证。`--no-shutdown` 会走同样流程但最后保持实例运行。

守护脚本遇到训练失败、提前停止、adapter 缺失、GPU 查询持续异常或仍有其他 GPU 进程时不会关机；状态文件会写明原因。这能避免把失败或别人的任务当成训练完成。失败后实例仍会运行并可能继续计费，需要查看状态或另设平台级空闲停机策略。[AutoDL 官方省钱文档](https://backup.autodl.com/docs/save_money/)也说明了 `/usr/bin/shutdown` 的用法。当前未启动正式训练，也未启用真实自动关机。
