# 赛题 4：双 48 GiB 上的 LoRA 与 QLoRA 短程实测（2026-10-11）

## 结论与边界

Qwen3.5-9B 已在服务器的两张约 48 GiB GPU 上完成 **BF16 LoRA 和 4-bit QLoRA 的前向、反向、参数更新与适配器保存**。这轮只训练了 3 步长样本和 5 步实际 fit 混合样本，证明环境、数据和双卡入口可以工作，**不代表模型效果已经验证，也不是完整微调**。测试集没有参与训练、测速或调参；没有向赛事平台提交。

在真实 fit 混合样本的 5 步对照中，BF16 LoRA 用时 161.57 秒，QLoRA 用时 209.99 秒；在三条接近 16K token 的压力样本中，次序相反（93.28 秒与 60.62 秒）。短跑显示速度受样本长度和量化实现影响，不能只根据参数量或一次测速断言谁始终更快。两种适配器的最终任务质量尚未比较。

若现在只选一条路线先完成包隔离验证，建议先跑 **BF16 LoRA**：在实际 fit 混合样本短跑中更快，两卡观测显存仍有余量，也避免 4-bit 底座量化误差。这个选择是当前机器与数据上的工程判断，不是质量结论。两卡均参与了数据并行训练，但尚未做严格单卡对照，不能声称吞吐翻倍。

## 数据与输出格式

训练只读取赛事原始训练集。服务器核对到 1000 包、7196 道 gold 题；包与相同文档分组清单固定为 fit/validation/holdout = 801/101/98 包。原始金标完整备选链仍保存在数据行元数据中；每次监督选一条同题完整备选链，没有拼接不同路径。全量检查 `fit_mixed_fixed_1epoch.jsonl` 的 5781 行及注册给 LLaMAFactory 的 5769 行：每行的消息角色均为 `system/user/assistant`，assistant 内容都可解析为且仅含 `answer`、`evidence_chain` 的 JSON，所选链均属于该行兼容的完整 gold 备选链；发现 0 项格式或链来源错误。

注册数据采用 LLaMAFactory 的 ShareGPT `messages` 列和 `qwen3_5_nothink` 模板。模型 tokenizer 与实际模板测得 12 行超过 16384 token，已记录在 manifest 并从本次 16K 数据注册中排除，原始行仍保留，**没有静默截断**。本次一轮训练候选为 5769 行，A/B/C = 3424/1758/587；最长写入序列 16356 token。数据及适配器均在 Git 忽略的 `outputs/`。数据源 SHA-256 为 `72ae65d73a5de6cf298c3df549ad1c40fbdac6894cb3d6945560acc2bc11fe23`，注册数据 SHA-256 为 `a72b9395bc000312a96d30bed214251822aa66ece2cc4cccbc9cdd5200985168`；明细见服务器 `outputs/llamafactory_qwen35_1pass_16k/manifest.json`。

老师提出的 JSON 监督建议与现有方案一致。推理输出也必须使用与训练完全相同的模板。实测发现旧 `run_sft.py` 在 Transformers 5.6.0 下把 `BatchEncoding` 当作 token 列表，且 Hugging Face 默认模板比训练模板多四个思考标记。现已改为 LLaMAFactory 的同一 `qwen3_5_nothink` 模板；对一条训练行逐 token 比较，两侧 prompt 完全一致（5528 token）。推理解析器只容许一个完整的前置 `<think>...</think>` 块，然后严格解析最终 JSON 并校验证据 ID。短训后的首道验证题原始输出是空思考块加合法 JSON，修复后通过解析；**单题格式通过不表示答案正确**。修正模板后，全部 2124 条 A/B/C 验证视图输入在 32768 token 推理预算内，无超长条目。

## 环境和实测

- 服务器有两张显示为 NVIDIA GeForce RTX 4090 的卡，每张报告显存 49140 MiB；PyTorch 分别在两卡上完成 CUDA 张量计算。PyTorch `2.6.0+cu124`、Transformers `5.6.0`、LLaMAFactory `0.9.5`（上游 commit `7af909522a951e3ad9f022ea6f88b6755257eaa5`）。快速算子导入检查通过，长样本训练未见回退警告。
- 两法均为 rank 16、alpha 32、dropout 0.05、目标层 `all`、BF16 计算、梯度检查点、Liger、同一模型与训练模板。可训练参数均为 43,278,336。QLoRA 另外使用 bitsandbytes 4-bit 和 double quantization。
- 两卡以 LLaMAFactory `FORCE_TORCHRUN=1` 数据并行启动。首次启动发现 shell PATH 未包含虚拟环境的 `torchrun`，在模型加载前失败；在命令 PATH 前置虚拟环境 `bin` 后成功。没有修改或覆盖原虚拟环境。

| 数据与有效 batch | BF16 LoRA | 4-bit QLoRA | 观察 |
| --- | ---: | ---: | --- |
| 3 条长样本；最大 16356 token；batch 2；3 步 | 93.28 秒 | 60.62 秒 | 两法均完成，loss 有限；LoRA 较慢 |
| 完整 fit 注册数据中按固定种子抽取；batch 8；5 步、40 样本 | 161.57 秒 | 209.99 秒 | 两法均完成，LoRA 较快 |
| 5 步平均优化步时间 | 32.31 秒 | 42.00 秒 | 含短跑首步开销与长度波动 |
| 根据 722 步线性外推的一轮训练段 | 约 6.5 小时 | 约 8.4 小时 | **只作租机预算参考**；不含预处理、保存、验证、重试 |

`nvidia-smi` 在长样本训练期间观察到 LoRA 约 31–32 GiB/卡、QLoRA 约 20 GiB/卡；这是瞬时读数，**不是峰值显存**。两卡数据并行各保存一份模型，显存不合并。长样本与混合样本得出的速度排序不同，因此正式选择要兼顾长样本占比、完整一轮成本和固定 validation 的效果；本轮没有用训练 loss 比较模型优劣。

### 训练完成后自动关机

`experiments/train_shutdown_guard.py` 启动并监控训练进程。只在进程返回 0、最终适配器和训练记录存在、`global_step == max_steps` 且达到指定最低步数后，开始统计 GPU 空闲。**两张卡均满足利用率不高于 5%、显存占用不高于 2048 MiB、无计算进程，连续 3 分钟**，才调用本机平台的 `/usr/bin/shutdown`；任何一张卡忙碌或查询失败都会重新计时。每 30 秒采样一次，所以实际触发可能略晚于 3 分钟。训练失败、产物不完整或等待超时均保留服务器供排错。

正式选择 LoRA 并确认数据盘空间后，可用下面的命令启动；日志和状态写入 Git 忽略的 `outputs/`。`--min-steps 722` 对应本配置 5769 行、有效 batch 8 的单轮预期步数。**目前没有执行这条整轮命令，也没有实际触发关机。**

```bash
cd /root/autodl-tmp/event-causal-chain-repo
nohup /root/autodl-tmp/task4-qwen35-venv/bin/python \
  experiments/train_shutdown_guard.py \
  --config experiments/configs/task4_qwen35_9b_fit1pass_lora_ddp2.yaml \
  --gpu-indices 0,1 --min-steps 722 \
  --utilization-limit 5 --memory-limit-mib 2048 \
  --idle-minutes 3 --poll-seconds 30 --arm-shutdown \
  > outputs/llamafactory_logs/fit1pass_lora_ddp2.guard.log 2>&1 < /dev/null &
```

已用专门的一步双卡 LoRA 配置做真实训练演练：两个 GPU 都参与训练，产物检查通过；以 `--no-shutdown --idle-minutes 1` 验证等待与终态，63 秒后得到 `verified_no_shutdown`。该演练**没有调用实际关机命令**。自动关机的最后一步仅由模拟单元测试覆盖；正式 3 分钟阈值沿用同一计时逻辑。演练配置是 `experiments/configs/task4_qwen35_9b_guard_ddp2_dryrun.yaml`。
